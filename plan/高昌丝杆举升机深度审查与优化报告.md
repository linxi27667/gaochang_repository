## 3. 总体结论

当前代码已经有雏形：四继电器时序、双柱平衡、上/下限位、防撞接口、W25Q高度保存、RS485 DMA框架都已出现。但以工业举升机标准看，当前工程不能直接上真机。原因不是小 bug，而是几类硬风险叠加：

1. 继电器 GPIO 上电默认值与低电平吸合逻辑冲突，存在上电误吸合风险。
2. 仿真编码器和仿真防撞逻辑仍被真机控制任务调用。
3. 下降方向真实编码器中断只做 `pulse_count++`，与下降高度应减少的控制逻辑冲突。
4. 按键数组只初始化了上升/下降，却读取停止/确认，存在空端口访问风险。
5. FreeModbus尚未接入当前工程；RS485现在只是回显测试，不具备HMI参数交互能力。
6. W25Q高度使用单扇区每5秒擦写，长期运行会集中磨损，并且写Flash发生在运动任务中。
7. CMake当前无法构建通过，Keil工程与CMake工程存在源文件/路径差异。

## 4. 代码严重问题清单

### P0-1 继电器上电默认吸合风险

位置：`code/f407zet6/Core/Src/gpio.c:54-56`  
现状：`PC0|PC1|PC2|PC3|PC4|PC5` 初始化前被写成 `GPIO_PIN_RESET`。  
项目约定：`RELAY_ON = GPIO_PIN_RESET`，低电平吸合，见 `APP/Inc/motor.h:46-48`。

风险：MCU启动执行 `MX_GPIO_Init()` 后，左主、右主、上升、下降相关输出可能被置为吸合态。对三相继电器控制来说这是不能接受的，尤其方向继电器和主接触器组合有误动作风险。

建议：所有继电器输出上电默认必须为 `RELAY_OFF = GPIO_PIN_SET`。初始化顺序应为：

1. 先写安全电平 HIGH。
2. 再初始化为推挽输出。
3. 再调用不含 RTOS 延时的 `Motor_Hardware_All_Off()` 做二次确认。

### P0-2 仿真逻辑混入真机运行链路

位置：`APP/Src/safety.c:198`、`APP/Src/safety.c:207`、`Driver/Src/dri_debug.c:19-95`  
现状：`Safety_Running_Update()` 每次运行都调用 `Sim_Encoder_Run()` 和 `Sim_Collision_Check()`。

风险：

- 真机接近开关中断已经在 `encoder.c` 计数，仿真函数会额外伪造脉冲。
- `COLLISION_ENABLE == 0` 时，仿真防撞在 500mm 自动触发停机报警；这会让真机调试行为异常。

建议：仿真代码必须用 `#if SIMULATION_ENABLE == 1` 完全隔离，真机固件不得链接或调用 `dri_debug.c`。

### P0-3 下降方向计数错误

位置：`APP/Src/encoder.c:20-31`、`APP/Src/balance.c:35-42`、`APP/Src/safety.c:137-153`  
现状：真实输入捕获中断无论上升还是下降都执行 `pulse_count++`。但下降平衡算法假设“脉冲少=降得快”，下限位保护也用 `pulse_count <= 0` 判断到底。

风险：下降过程中真实高度计数会越来越大，导致：

- 下限位软件保护基本失效，只能依赖PB0硬件下限位。
- 下降平衡算法方向判断不成立。
- 高度保存越降越高，HMI显示不可信。

建议：编码器ISR根据 `g_command.direction` 做方向计数：

- `DIR_UP`：`pulse_count++`
- `DIR_DOWN`：`pulse_count--`，最小钳位到 0

同时，下降方向也要更新 `last_pulse_tick`，并对异常负数做报警。

### P0-4 按键数组初始化不完整

位置：`APP/Src/key.c:10-13`、`APP/Src/key.c:59-65`  
现状：`MAX_KEY_NUM = 4`，但 `g_key` 只初始化了上升键和下降键。后续读取 `g_key[2]` 停止键、`g_key[3]` 确认键。

风险：`g_key[2].port` 和 `g_key[3].port` 为 0，`HAL_GPIO_ReadPin(NULL, 0)` 在真机上可能HardFault，停止键和二次确认功能也不会可靠工作。

建议：补齐：

- `[2] = { .port = KEY_STOP_PORT, .pin = KEY_STOP_PIN }`
- `[3] = { .port = KEY_CONFIRM_PORT, .pin = KEY_CONFIRM_PIN }`

### P0-5 防撞输入未真正启用，触发沿也不一致

位置：`Core/Inc/main.h:93`、`Core/Src/gpio.c:87-91`、`APP/Inc/safety.h:34-38`  
现状：

- `COLLISION_ENABLE` 为 0。
- 注释要求 PB1/PB2 防碰杆 falling edge，但 `gpio.c` 把 PB0/PB1/PB2 全部配置成 rising edge。
- PB0下限位、PB1/PB2防撞共用同一种触发配置，无法表达不同触发沿。

建议：

- 真机版本 `COLLISION_ENABLE` 必须为 1。
- PB0按下限位实际电路配置 rising/falling。
- PB1/PB2按防撞杆实际常闭/常开电路单独配置触发沿，建议常闭回路断开触发，软件里同时读引脚确认状态。

### P0-6 `Motor_Init()` 在调度器启动前调用 `osDelay`

位置：`Core/Src/main.c:121`、`APP/Src/motor.c:25-28`、`APP/Src/motor.c:93-108`  
现状：`Motor_Init()` 调用 `Motor_Stop_All()`，内部有 `osDelay(10)`。此时 `osKernelInitialize()` 还没执行。

风险：CMSIS/FreeRTOS延时在调度器启动前行为不可靠，可能卡住或触发断言。

建议：拆成两个函数：

- `Motor_Hardware_All_Off()`：无延时，用于上电初始化和中断急停。
- `Motor_Stop_All()`：任务上下文使用，可包含灭弧延时。

### P1-1 FreeModbus尚未接入

位置：`Driver/Src/dri_rs485.c:15-39`、`APP/Src/app_rs485.c:105-155`  
现状：RS485任务每2秒发送自检字符串，并把收到的数据回显。工程内没有 `eMBInit()`、`eMBEnable()`、`eMBPoll()`，也没有 `eMBRegHoldingCB()` 等寄存器回调。

结论：当前不能与 Kinco GL070/GL070E 进行参数和高度数据的 FreeModbus 交互。硬件链路具备基础条件，但协议层尚未完成。

### P1-2 当前RS485接收回调方式可能不触发

位置：`APP/Src/app_rs485.c:11-15`、`APP/Src/app_rs485.c:151-155`、`Core/Src/usart.c:303-306`  
现状：使用 `HAL_UART_Receive_DMA()` 启动接收，然后期待 `HAL_UARTEx_RxEventCallback()` 更新FIFO head。

风险：ST HAL的 Receive-to-Idle 回调通常应由 `HAL_UARTEx_ReceiveToIdle_DMA()` 启动。仅 `HAL_UART_Receive_DMA()` 加 IDLE 中断，未必会进入 `HAL_UARTEx_RxEventCallback()`。这会导致 `RS485_Available()` 长期为0。

建议：若继续使用DMA方案，改为 `HAL_UARTEx_ReceiveToIdle_DMA()`；若接入FreeModbus RTU，建议按FreeModbus原生模型改为RXNE/TXE字节中断 + T3.5定时器。

### P1-3 USART2_TX 引脚文档与代码不一致

位置：`plan/项目交接日志.md`、`Core/Src/usart.c:172-188`、`Core/Src/gpio.c:73-78`  
文档写法：USART2_TX = PA2，USART2_RX = PA3。  
代码实际：USART2_RX = PA3，USART2_TX = PD5；PA2被配置成普通输出并置高。

建议：必须按PCB实物重新核对。若RS485模块接在PA2/PA3，则当前固件TX不会出现在PA2；若模块接在PD5/PA3，则文档和接线表要更新。

### P1-4 W25Q高度存储单扇区集中磨损

位置：`APP/Src/app_w25qxx.c:221-255`、`APP/Src/app_w25qxx.c:260-277`  
现状：运行中脉冲变化时，每5秒擦除并重写 `HEIGHT_FLASH_ADDR = 0x00002000` 一个固定扇区。

风险估算：W25Q系列常见扇区擦写寿命约10万次。若固定扇区每5秒擦一次，理论连续运动约 `100000 * 5s = 138.9小时 = 5.8天` 达到擦写寿命量级。实际设备不是连续运动，但这个设计仍然把寿命风险集中在一个扇区。

建议：

1. 高度不要运行中固定周期擦写。
2. 改为“停止后延迟保存”和“掉电保持保存”。
3. 高度用日志式磨损均衡：例如预留64个或128个4KB扇区，每条记录带 `magic + seq + heights + crc + commit`，启动时扫描最大 `seq`。
4. 若高度必须频繁保存，建议增加 I2C/SPI FRAM，例如 MB85RS/MB85RC 系列，保留W25Q只存参数、日志和HMI资源。

### P1-5 配置结构没有真正持久化

位置：`APP/Inc/app_w25qxx.h:26-40`、`APP/Src/app_w25qxx.c:12-25`、`APP/Src/app_w25qxx.c:129-184`  
现状：`w25q_config_t g_config` 定义了最大高度、允差、堵转时间等，但 `w25q_storage_t` 只保存了 `debug_counter`，没有保存 `g_config`。

风险：HMI即使通过Modbus写入最大高度/导程/允差，重启后也会丢失。

建议：定义统一的 `persist_config_t`，包含版本号、配置、统计、CRC32，并用双槽或日志式保存。

### P1-6 CMake当前构建失败

验证命令：

```powershell
cmake --preset Debug
cmake --build --preset Debug
```

结果：配置成功，构建失败。主要错误：

- `bsp_uart_dma.h` 找不到 `fifo.h`，因为 `Middlewares/FIFO` 未加入CMake include，`fifo.c` 也未加入源文件。
- CMake使用GCC工具链，却包含 `portable/RVDS/ARM_CM4F`，导致 `__forceinline`、`msr` 等ARMCC语法报错。

建议：

- CMake include 增加 `Middlewares/FIFO`。
- sources 增加 `Middlewares/FIFO/fifo.c`。
- GCC构建应使用 `Middlewares/Third_Party/FreeRTOS/Source/portable/GCC/ARM_CM4F`，若仓库没有该目录，需要补齐或只使用Keil/RVDS工程。

### P2-1 任务栈与堆偏小

位置：`Core/Inc/FreeRTOSConfig.h:71`、`Driver/Src/dri_rs485.c:10`、`Driver/Src/dri_safety.c:11`  
现状：`configTOTAL_HEAP_SIZE = 15360`，RS485任务栈256字，Safety任务栈256字。

风险：后续引入FreeModbus、MQTT、JSON、HMI参数处理后，15KB总堆和小栈会偏紧。

建议：

- Modbus任务：512-1024 words。
- 通信/MQTT任务：至少1024-2048 words，若JSON解析则更高。
- 开启 `configCHECK_FOR_STACK_OVERFLOW = 2` 和 `configUSE_MALLOC_FAILED_HOOK = 1`。
- 关键任务优先考虑静态创建。

## 5. Kinco GL070/GL070E 与FreeModbus可行性

结论：硬件和协议可行，但当前代码尚未完成。

依据：

- Kinco官方GL070E页面列出通讯接口为 `COM0: RS232/RS485/RS422; COM2: RS232`，组态软件为 DTools V4.1及以上。
- Kinco GL070/GL070E安装说明写明 COM0 支持 RS232/485/422，COM2只支持RS232；RS485引脚为 1脚B、6脚A、5脚GND。
- Kinco DTools Pro教程展示了HMI作为Master，通过COM0选择Modbus、Modbus RTU Extend、RS485、9600/8/N/1，连接外部Slave设备。

因此推荐主从关系：

```
Kinco HMI COM0 RS485 作为 Modbus RTU Master
STM32F407 USART2 RS485 作为 Modbus RTU Slave
```

注意：

- GL070E有以太网；基础GL070是否具备以太网要按实际型号确认。若是普通GL070，联网不要依赖屏幕，应由后续4G IoT模块完成。
- Modbus RTU一条总线上只应有一个Master。若后续4G模块也要主动轮询STM32，不能和HMI同时作为Master挂在同一条RS485上。

## 7. FreeModbus接入方案

### 7.1 不建议直接把当前DMA回显任务改成Modbus

FreeModbus RTU内部是字节状态机，依赖串口收发事件和T3.5定时器。当前DMA FIFO设计更像自定义帧协议，和FreeModbus原生事件模型不完全匹配。

推荐路线：

1. 保留 `APP/Src/app_rs485.c` 作为底层串口封装，但停止 `dri_rs485.c` 的回显测试。
2. 在 `Middlewares/FreeModbus` 放入协议栈源码，工程内加入：
   - `mb.c`
   - `mbrtu.c`
   - `mbcrc.c`
   - `mbfuncholding.c`
   - `mbfuncinput.c`
   - `mbfunccoils.c` 可选
   - `mbutils.c`
   - STM32 port: `portserial.c`、`porttimer.c`、`portevent.c`
3. USART2用于Modbus RTU，TIM3或TIM7用于T3.5定时器。
4. 新建 `APP/Src/modbus_map.c` 实现寄存器读写回调。
5. 新建 `Driver/Src/dri_modbus.c` 任务：

```c
void Modbus_Task(void *arg)
{
    eMBInit(MB_RTU, g_config.modbus_slave_id, 2, 9600, MB_PAR_NONE);
    eMBEnable();
    while (1) {
        eMBPoll();
        osDelay(1);
    }
}
```

### 7.2 Kinco DTools配置建议

1. COM0选择 RS485。
2. HMI作为Master，STM32作为Slave。
3. Protocol选择 Modbus RTU 或 Modbus RTU Extend。
4. 推荐先用 9600/8/N/1 调通，再提高到 115200/8/N/1。
5. GL070/GL070E COM0接线：
   - Pin 6 = RS485 A
   - Pin 1 = RS485 B
   - Pin 5 = GND
6. DTools变量使用4x寄存器，显示高度、报警、状态；参数页写40100以上；按钮写40200命令区。

## 8. 后续4G IoT/MQTT通信方案

不要让HMI和4G模块同时作为Modbus Master挂同一条RS485总线。

推荐拓扑：

```
Kinco HMI COM0 RS485  <-->  STM32 USART2 Modbus RTU Slave

4G IoT模块 UART/RS485 <-->  STM32 USART1 或 USART3 透明AT/MQTT协议
                              |
                              +--> MQTT服务器
                                      |
                                      +--> APP
```

STM32内部做统一数据模型：

- `lift_status_t`：高度、方向、报警、输入输出、举升次数、保养计数。
- `lift_config_t`：最大高度、最低位、允差、二次下降高度、设备ID。
- `lift_command_t`：清零、调平、报警复位、远程作业高度、车辆信息。

HMI和MQTT都只读写这套模型，禁止各自直接操作继电器。

MQTT Topic建议：

- `lift/{device_id}/status`
- `lift/{device_id}/alarm`
- `lift/{device_id}/config/report`
- `lift/{device_id}/cmd`
- `lift/{device_id}/cmd_ack`

远程命令必须加权限、序号、超时和本地确认。涉及运动的远程命令建议只下发“目标参数/工单”，不直接远程启动电机。

## 9. W25Q存储优化方案

### 9.1 当前存储布局问题

当前定义：

- `0x00000000` Slot A：debug storage
- `0x00001000` Slot B：debug storage
- `0x00002000` Height：固定高度扇区

问题：

- 配置参数没有进入持久化结构。
- 高度固定扇区磨损。
- 运行中擦写Flash会阻塞控制任务。
- W25Q80/W25Q128型号描述不一致，初始化读取JEDEC后没有校验。

### 9.2 推荐布局

以W25Q80 1MB为例：

| 区域 | 地址范围 | 用途 |
|---|---|---|
| Sector 0-3 | 0x000000-0x003FFF | Boot/生产信息/设备序列号，只写少量 |
| Sector 4-7 | 0x004000-0x007FFF | 配置双槽保存 |
| Sector 8-71 | 0x008000-0x047FFF | 高度日志磨损均衡，64扇区 |
| Sector 72-127 | 0x048000-0x07FFFF | 故障日志、举升次数、保养记录 |
| 其余 | - | 预留HMI/IOT/升级数据 |

### 9.3 高度保存策略

推荐顺序：

1. 运行中只更新RAM高度。
2. 停止后 2-5秒 若高度变化，再写入一次。
3. 下限位清零时立即写入一次。
4. 参数保存时单独写配置区。
5. 若需要掉电保存，硬件增加掉电检测输入和储能电容，检测到电源跌落后立刻停止电机并写最后高度。

记录格式：

```c
typedef struct {
    uint32_t magic;       // "HLOG"
    uint32_t seq;
    int32_t  pulse[2];
    uint16_t state;
    uint16_t reserved;
    uint32_t crc32;
    uint32_t commit;      // 最后写 0xA55A5AA5
} height_log_record_t;
```

启动时扫描日志区，选择 `commit` 有效、CRC正确、`seq` 最大的记录。

### 9.4 是否会因为多次擦除导致高度不准

会，但表现不是“慢慢偏一点”，而是某个扇区到寿命后出现擦不干净、写不进去或读回CRC错误。当前代码如果固定扇区失败，启动时可能无法加载高度，继而高度回到默认0或旧值，造成高度显示和安全限位不准。

更好的办法：

- 高频高度：FRAM最佳。
- 中频高度：W25Q日志式磨损均衡。
- 低频参数：W25Q双槽保存即可。

## 12. 控制策略建议

### 12.1 电机状态机

不要让多个任务直接调用 `Motor_Start_All()` / `Motor_Stop_All()`。建议统一成状态机：

```
IDLE
  -> PREPARE_UP / PREPARE_DOWN
  -> RUN_UP / RUN_DOWN
  -> BALANCE_WAIT
  -> STOPPING_ARC_DELAY
  -> ALARM_LOCKED
  -> MAINTENANCE_MANUAL
```

所有HMI、按键、IoT命令都只写“意图”，由控制任务统一判定安全条件后执行。

### 12.2 防撞杆逻辑

防撞触发后：

- 立即切断所有运动。
- 记录 `ALARM_COLLISION`。
- 禁止继续上升。
- 允许按下降键解除上限/防撞锁并下降，但下降前应要求用户松开再按，避免中断触发瞬间直接反向动作。

### 12.3 一键调平

建议作为维护功能，不作为普通用户按钮：

- 条件：运动停止、无载或维护确认、无防撞/堵转报警。
- 目标：两柱脉冲差回到0或允差内。
- 策略：只移动低的一侧向上追平，避免自动下降造成机械风险；若必须下降，进入维护模式并低速点动。
- 超时或无脉冲立即报警。

## 13. 验证计划

### 13.1 静态检查

1. CMake必须构建通过。
2. Keil工程和CMake工程源文件一致。
3. 所有真机构建不得包含 `dri_debug.c`。
4. `main.h` 中硬件开关必须有 `#error` 防止调试配置误烧真机。

### 13.2 台架测试

1. 不接电机，只接继电器指示灯，上电确认所有继电器OFF。
2. 按上升：先方向后主接触器，下降同理。
3. 上升/下降方向切换：确认先断主接触器，延时后切方向。
4. 防撞触发：上升立即停；再次上升禁止；下降允许。
5. 下限位：触发后两柱高度清零并写入存储。
6. 拔掉一路接近开关：堵转/无脉冲超时报警。
7. 两柱脉冲人为错开：差值超过4暂停快柱，追平恢复。

### 13.3 HMI通信测试

1. 用USB-RS485和Modbus Poll先模拟HMI，读40010/40011高度。
2. 写40100最大高度，读回确认。
3. 写40200/40202触发清零，查看40203/40204应答。
4. Kinco DTools接入COM0，逐项绑定寄存器。
5. 做断电重启，确认参数和高度恢复正确。
